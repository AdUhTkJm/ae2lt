# AE2 的内部实现

AE2 最值得称道的地方就是它的自动合成功能。这篇文档将介绍它的内部实现。

AE2 会先生成一个**合成计划**，然后再用 CPU 执行它。

## 生成合成计划

### 样板

合成计划需要基于样板生成，而样板的信息都存储在 `IPatternDetails` 接口内部。

这个样板信息自然需要储存输入以及输出。由于 AE 网络中可能有物品、流体之类的不同内容，我们需要一个统一的类型（接口）来表示它们。这个类型是 `GenericStack`，其中含有资源的标识符以及数量。这里的标识符的类型是抽象类 `AEKey`，有 `AEItemKey`, `AEFluidKey` 等子类。

由于某些合成表会留下空桶，输入并不能只保存单个的 `GenericStack`，还需要告知网络可能会留下什么。而且，许多合成表中使用的是物品标签而不是某个确定的物品，所以输入可能有不止一种。因此， AE2 设计了 `IInput` 接口来承载输入内容，它提供了上面的方法（`getRemainingKey()`, `getPossibleInputs()`）。

至于输出，AE2 的自动合成规划只能处理**一种***主要输出* (`getPrimaryOutput()`)。其他的输出都是副产物，在规划时会被忽略。

同样地，AE2 的规划也只能处理**一种***主要输入*，这是 `IInput#getPossibleInputs()` 的第一个元素。其它的变种可以参与合成，但是不会被规划器从其他的材料合成。

### 启动规划

在收集完所有样板后，我们就可以开始规划了。

尽管我们期望合成规划是在后台计算的，但其实 AE2 并未这么做。这是因为合成规划可能需要来自主线程的信息。 例如：

- 在计算时，需要查询网络里到底有什么东西。
- 在模糊匹配/按标签匹配时，每次都需要去主线程的 `level` 处查询 `RecipeManager` 之类的内容，来确定这个匹配到底对不对。

而 Minecraft 的这些数据都不是线程安全的，因此单线程是合适的。即使是用锁，在这种情况下，粗粒度的锁跟串行区别不大。

为了防止一次计算卡死整个游戏，AE2 采用了协程。每个 tick 中都会有 5 毫秒用来计算，如果有不止一个任务，那么它们均分。当时间片结束后，主线程恢复运转。这意味着在 AE2 的计算线程中访问主线程将会导致死锁。

这里的 `CraftingCalculation#handlePausing()` 就是在做 yield 的工作，当时间到了之后放弃自身的时间片。每计算完一个节点都需要调用它一次，以防超时。它也做了一点小优化：每 100 次调用只进行一次 `System.nanoTime()`，减少访问时钟的额外开销。

既然我们无法在规划时访问主线程，我们需要在开始时就生成当前网络中物品的快照。这是由 `NetworkCraftingSimulationState` 所做的。它的继承链路如下：

**最上层**
```
ICraftingInventory:
    - insert
    - extract
    - findFuzzyTemplates: AEKey -> Iterable<AEKey>
```
一个没有储存上限（实则为 long 上限）的物品栏，只支持插入、删除与模糊查找。

既用于规划，也用于 CPU 的储存，所以刻意地很抽象、方法很少。

**第二层**
```
ICraftingSimulationState:
    - emitItems: AEKey * long -> unit
    - addBytes
    - addCrafting: IPatternDetails * long -> unit
```
可以看出来这就是专用于合成规划的 `ICraftingInventory`，能储存合成产物和合成方式，以及可以计算合成所需的字节数。

**第三层**
```
CraftingSimulationState:
    - simulateExtractParent: AEKey * long -> unit
    - findFuzzyParent: AEKey -> Iterable<AEKey>
```
这是个抽象类，提供了第二层 `ICraftingSimulationState` 的所有方法实现，不过给子类留了这两个抽象方法。

这里的 `findFuzzy` 模糊匹配其实没啥好说的，而 `simulateExtract` 相当于是 `extract(..., ActionMode.SIMULATE)`，所以不会真实地提取物品，而只是模拟提取并返回提取出的数量。

它的内部实现是维护了两个 `KeyCounter`，换言之也就是 `Map<Object, Long>`，用来记录物品的初始数量和当前数量。前者叫做 `unmodifiedCache`，也就是创建之后不会修改；后者叫做 `modifiableCache`，会在 `insert`, `extract` 等接口处根据物品变化而改动。

在需要提取物品的时候，如果 cache 中没有，AE2 会尝试提取最大数量的、所有能模糊匹配上的物品，然后将它们加入这两个 cache 中，后续就只操作 cache 了。这就是 `cacheFuzzy` 这个私有函数所做的事情。

**第四层**

总算到了 `NetworkCraftingSimulationState`。它会复制一份网络的当前存储，然后基于此实现最后需要的两个方法。

与之相对地，还有另一个 `ChildCraftingSimulationState` 也在这一层，是对 `ICraftingInventory`（第一层）的一个包装。注意到这两个需要实现的函数都是只读的，所以直接持有引用是没有问题的。

### 合成树

在规划时，重要的就是合成树的节点了。不过一共有两类节点：一个**样板**可以是一个节点，它可能需要几个输入物品；一个**物品**可以是一个节点，它可能需要用于合成它的样板。

AE2 中：
- `CraftingTreeNode` 是**物品**的节点，会以样板作为父/子节点。
- `CraftingTreeProcess` 是**样板**的节点，会以物品作为父/子节点。

我们的根节点肯定是**物品**节点，是我们要合成的东西。这里可能会有模糊匹配。

接下来就是 DFS 环节。我们的 `CraftingCalculation` 会调用 `CraftingTreeNode#request`，它接受一个物品栏、需要合成的数量以及一个用于输出的合成残余物列表。这里就是我们在[样板](#样板)一节提到的 `IInput#getRemainingKey`，或者说是“合成留下来的桶”。 这里叫做 `containerItem`，确实术语不太一致。

然后，在 `request` 内部，它会依次执行三个内容：
- 取出已有的物品；
- 如果有创造 ME 元件的话，直接生成物品（这里的术语是 `emit`）；
- 寻找能合成它的模板，并将这些模板设置为物品节点的孩子。如果只有一个模板，那么自然就直接往死里用；如果多于一个，就第一个检测完之后接下一个，直到完成为止。

和普通的 Capability 类似，这里也有 Simulation 和 Execute 的区分。

### 合成计划

在构造一棵合成树之后，我们就可以得到合成的完整计划了。它不需要是一棵树，只需要保存这些内容就可以了：

- 哪个样板，发送几次；
- 需要从网络中提取/凭空生成什么；
- 还缺什么；
- 实际合成的物品数量；
- 字节数。

所以，我们只需要将树结构转换一下即可。保存这个的显然是个 record，叫做 `CraftingPlan`。

## 执行计划

首先，我们需要考虑到在执行计划时，区块可能会卸载、玩家可能会退出游戏。所以 AE2 用 `CraftingLink` 来持久化这些内容。

我们需要记住是哪个机器发布了这个请求，以及是哪个 CPU 在执行它。因此 `CraftingLink` 里有两个互斥的字段 `req` 和 `cpu`，一方用一个。对于玩家发送的请求，只需要 CPU 记住就可以了，因此没有 `req` 这一端。 我们还有 `ExecutingCraftingJob` 来记录具体进行到了哪里。

CPU 会主动向样板供应器推送物品，然后等待样板供应器返回。这个玩 AE2 的应该都很熟悉，我就不多说了。这一切都是在 `CraftingCpuLogic` 这个类里进行的。
